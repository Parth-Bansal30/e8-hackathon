# Handoff: external memory tests (OSPI flash and PSRAM)

What the second machine needs to build and run the two new memory tests, `flash_test` and
`psram_test`, and what they should print. The base setup is in [HANDOFF.md](HANDOFF.md). The
findings and board quirks are in [bringup-notes.md](bringup-notes.md#external-memory-ospi).

Snapshot date: 2026-10-18. Reference board: DK-E8, AE822FA0E5597LS0, chip revision A0.

---

## 1. What was found

The pack 2.0.4 board files are wrong about both external memories on this kit:

| Memory | Pack 2.0.4 says | Actually fitted | CPU read speed (D-cache on) |
|---|---|---|---|
| Flash, OSPI1, XIP at `0xC0000000` (read-only) | ISSI octal NOR, 32 MB | ISSI octal NOR, **64 MB** | 74 MB/s sequential, 469 ns random |
| RAM, OSPI0, XIP at `0xA0000000` (read/write) | ISSI HyperRAM, 32 MB | AP Memory **APS512XXN PSRAM, 64 MB**, used x8 | 107 MB/s read, 113 MB/s write, 347 ns random |
| MRAM, on-chip (reference) | 5.5 MB | 5.5 MB | 201 MB/s |

Flash through the CMSIS driver: a 4 KB erase takes about 82 ms, programming runs at about
1.1 MB/s and register-mode reads at 9.2 MB/s.

Not tested yet: whether the Ethos-U85 can read weights through either window.

## 2. Toolchain and dependency changes

**None.** Install the same versions as in [HANDOFF.md §2](HANDOFF.md#2-exact-software-versions):

- Alif pack `AlifSemiconductor::Ensemble` **2.0.4**. Don't upgrade to 2.2.x; the rest of the repo is built against 2.0.4.
- SETOOLS 1.112.00, with the A0 revision change in `global-cfg.db`.
- J-Link V9.86a.
- CMSIS-Toolbox 2.15.0, Arm GNU 13.3.1, CMake 3.31.12, Ninja 1.13.2.

Everything new lives in the repo:

No other repo files changed. The local `firmware/.vscode/*` edits on the reference machine

## 3. The PSRAM build settings

`psram_test.cproject.yml` doesn't use the pack's OSPI component because `vendor/ospi.c`
replaces it. **Never link both OSPI drivers into one project** (duplicate symbols, and the
2.0.4 driver doesn't know the address-control shim).

| Define | Value | Meaning |
|---|---|---|
| `RTE_APS512XXN_PSRAM_WAIT_CYCLES` | 4 | XIP read latency, the pack 2.2.1 E8 value |
| `RTE_APS512XXN_PSRAM_DUAL_OCTAL_MODE_ENABLE` | **0** | x8 on D0–D7, as on the AppKit-E8. x16 (1) stalls the bus at the first XIP access |
| `RTE_APS512XXN_PSRAM_OSPI_SS_LINE` | 0 | chip select 0 |
| `SOC_FEAT_AES_HAS_ADDR_CTRL_SHIM` | 1 | E8 silicon has the AES address-control shim; the 2.2.1 driver needs to know |
| `RTE_OSPI0_BUS_SPEED` / `_DFS` / `_WAIT_CYCLES` | 100000000 / 32 / 6 | present in 2.2.1's `RTE_Device.h`, missing in 2.0.4. Only `CONFIG_MODE_RTE` reads them; `main.c` doesn't use that mode |
| `RTE_OSPI1_BUS_SPEED` / `_DFS` / `_WAIT_CYCLES` | 100000000 / 32 / 3 | same |

`main.c` passes these settings to `ospi_psram_xip_init()` itself: instance 0, 100 MHz,
DDR drive edge 1, RXDS delay 11, signal delay 22, DFS 32, `RAM_TYPE_PSRAM`, octal frame format.
Its init hook resets the PSRAM (command 0xFF), reads MR0–MR2 in register mode, and only goes
on to `aps512xxn_psram_init()` if MR2's high byte is `0xDE`.

Reset pins (both on port 15, driven as GPIO): **P15_6 = PSRAM reset, P15_7 = flash reset**.
Pack 2.0.4's `board_defs.h` says P15_5 for the flash, which is really LCD_RESET.

```bash
cd ~/alif/e8-hackathon
git fetch origin
git switch ospi-memory-tests        # or main, once it's merged
git pull
```

If `firmware/vcpkg-configuration.json` resolved different versions on this machine before,
reopen `firmware/` in VS Code so the Environment Manager installs the pinned ones. Then check:

```bash
A=$(zsh -c 'print -l ~/.vcpkg/artifacts/*/tools.open.cmsis.pack.cmsis.toolbox/2.15.0(N:h:h) | head -1'); echo $A
```

An empty result means CMSIS-Toolbox 2.15.0 isn't installed yet.

## 5. Run the tests

The board must be on the **PRG USB** port (J3), with `isp_config_data.cfg` pointing at its
serial port as in [HANDOFF.md §3.4](HANDOFF.md#34-setools-flashing). Build + flash takes
10–40 s per project.

### 5.1 Flash test

```bash
tools/build_flash.sh flash_test
tools/rtt_dump.sh firmware/out/flash_test/E8-HP/debug/flash_test.elf
```

Expected (timings vary by a few percent):

```
[FLASH] OSPI1 flash test, core clock 400 MHz, D-cache on
[FLASH] MRAM sequential read (reference)  201.2 MB/s  (2048 KB in 10421 us)
[FLASH] driver config: 16384 sectors x 4096 B = 64 MB
[FLASH] 4 KB sector: erase 81720 us, program 3627 us, read 464 us
[FLASH] bad bytes: low sector 0, high sector 0, low after high write 0 -> 64 MB part
[FLASH] read (driver, register mode)        9.2 MB/s  (256 KB in 28395 us)
[FLASH] RESULT (driver): PASS
[FLASH] XIP read back: 0 / 0 bad bytes (low / high sector)
[FLASH] RESULT (XIP): PASS
[FLASH] XIP sequential read                74.2 MB/s  (4096 KB in 56504 us)
[FLASH] XIP random 4-byte read: 469 ns
[FLASH] done
```

It erases and rewrites only two 4 KB sectors, at `0x01F00000` and `0x03F00000` (31 MB and
63 MB). Nothing else in the flash is touched. If the second board has a 32 MB part, the line
says `32 MB part (wrapped)` and the driver result is `FAIL`. That's a real finding, not a bug.

### 5.2 PSRAM test

```bash
tools/build_flash.sh psram_test
tools/rtt_dump.sh firmware/out/psram_test/E8-HP/debug/psram_test.elf
```

Expected:

```
[RAM] OSPI0 PSRAM test (pack 2.2.1 driver), XIP wait cycles 4, octal x8
[RAM] APS global reset...
[RAM] reading mode registers...
[RAM] MR0 088d  MR1 8dde  MR2 dea0  (APS512XXN ID 0xde expected in MR2 high byte)
[RAM] APS512XXN found; configuring latency, burst and x8 mode
[RAM] XIP init ok
[RAM] first word: ...                      (whatever was left in the RAM)
[RAM] wrote 12345678 9abcdef0, read 12345678 9abcdef0
[RAM] detected size: 64 MB
[RAM] pattern pass 1 (64 MB): 0 errors
[RAM] pattern write (CPU)              29.0 MB/s  (65536 KB in 2307143 us)
[RAM] pattern verify (CPU)             25.7 MB/s  (65536 KB in 2607104 us)
[RAM] pattern pass 2 (inverted): 0 errors
[RAM] RESULT: PASS
[RAM] sequential read                 107.0 MB/s  (4096 KB in 39198 us)
[RAM] RAM -> DTCM memcpy              107.7 MB/s  (256 KB in 2433 us)
[RAM] DTCM -> RAM memcpy              113.5 MB/s  (256 KB in 2309 us)
[RAM] random 4-byte read: 347 ns
[RAM] done
```

The two 64 MB pattern passes take about 10 s, so run `rtt_dump.sh` again if the log stops at
`pattern pass 1`.

The test checks the RAM's ID before any memory-mapped access. On a board with a different RAM
it prints `not an APS512XXN` and stops, instead of hanging the bus. Send the MR0/MR1/MR2 line
back if that happens.

### 5.3 Put the keyword app back

```bash
tools/build_flash.sh app
```

## 6. If something goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| cbuild: `read …/firmware: is a directory` | first build of a newly added project, or after a clean | `rm -rf firmware/tmp firmware/out/<project>` and run the same command again. Sometimes it takes two tries |
| J-Link: `Failed to power up DAP` | the running program stalled the bus on an XIP access nobody answers (e.g. PSRAM in x16 mode, or the 2.0.4 HyperRAM driver) | the debugger can't attach while the bus is stalled. Flash `hello_rtt` with `tools/build_flash.sh hello_rtt` (SETOOLS doesn't need the DAP), then flash the test again |
| SETOOLS: board in **RECOVERY MODE**, or flashing refused after a hang | SEROM recovery state | `cd ~/alif/app-release-exec-macos && ./maintenance` → `1` (ROM) → `1` (MRAM Recovery). It sends about 397 KB at 57600 baud, which takes **about 130 s**. Don't interrupt it. It's safe to run again if it gets cut off |
| `[FLASH] FAIL: XIP setup` | the flash was still in octal DDR when `setup_flash_xip()` read its ID in SDR | `main.c` already pulses P15_7 before it. If you copy the code elsewhere, keep that reset |
| Timings print as 0, or the program hangs in a delay | J-Link clears `DEMCR.TRCENA` when it detaches, which stops the DWT cycle counter | the tests re-enable it on every read (`cycles()` in `main.c`); do the same in new code |
| Link error: undefined `aes_enable_xip` | missing `#include "sys_ctrl_aes.h"` | include it from `vendor/` |

## 7. Next steps for memory

1. **NPU access:** compile a model with Vela in `Dedicated_Sram` mode, put the weights in the
   flash XIP window (`0xC0000000`) or PSRAM (`0xA0000000`), and check the Ethos-U85 reads them
   and gives the same output as from MRAM. Measure the inference time.
2. If that works, large models no longer need to fit in MRAM (5.5 MB). Flash gives 64 MB for
   weights, and PSRAM gives 64 MB for activations or buffers.
3. Optional: find out why x16 (dual-octal) PSRAM stalls; it should roughly double the PSRAM bandwidth.
